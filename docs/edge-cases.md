# Edge Cases

Tracks specific failure-mode scenarios found while building this
system — as opposed to `decisions.md`, which tracks deliberate design
choices. When a new edge case turns up, add a row with status **Open**.
When it's fixed, flip it to **Handled** and add a one-line resolution
(link to the relevant `decisions.md` entry if there is one).

| # | Edge case | Status | Resolution |
|---|---|---|---|
| 1 | A skill (`specify`/`plan`/`tasks`/`implement`) pauses mid-run to ask the developer a question. `Stop` fires on that pause (not just on true completion), so a `*_completed` event could log too early and the real completion gets missed. | Open | Accepted risk — Spec-kit isolates clarification into its own skill (`/clarify`, out of scope), so this is low-probability for the four in-scope skills. Not solving now. See [decisions.md #9]. |
| 2 | `speckit-implement` has no single canonical output artifact (unlike `spec.md`/`plan.md`/`tasks.md`), so an artifact-write-based completion check doesn't generalize to it. | Handled | Moot — dropped artifact verification entirely in favor of a bare `Stop`-based completion signal, which applies uniformly to all four skills. See [decisions.md #9]. |
| 3 | Branch names in the real target repo (`mvnx-support-and-engagement-specs`) don't carry parseable Jira ticket IDs — the assumed `feature/ABC-123` convention doesn't hold (`faq-admin-page`, `poc-faq-tobi`, etc). | Handled | Dropped ticket-ID-based correlation entirely; correlation now derives from Spec-kit's own `.specify/feature.json`. See [decisions.md #11]. |
| 4 | `speckit-specify`'s correlation ID was read from `.specify/feature.json` at *start* time, but that file is still pointing at the previous spec — `specify` hasn't created/registered the new spec folder yet. Started and completed events for the same run could get different correlation IDs. **Found via real usage, not simulation** — this was the "big problem." | Handled | Mint a fresh UUID at start instead of reading `feature.json`; couple it to whichever spec folder is current once the skill actually finishes (marker file `specs/NNN-xxx/.telemetry.json`, committed to the repo). See [decisions.md #13]. |
| 5 | Re-running `/speckit-specify` to update an *existing* spec in place (not create a new one) — the fresh UUID minted at start won't match that spec's already-coupled correlation ID, so this run's own started/completed pair can end up orphaned from the spec's real history. | Open | Not solved — rarer than the create-new-spec path. See [decisions.md #13]. |
| 6 | The hook guesses the JSON key holding the skill name inside a `PostToolUse(Skill)` payload's `tool_input` (tried `skill`, then `name`) — never confirmed against a real live hook firing, only simulated stdin. If wrong, real skill runs would silently produce zero events. | Handled | Confirmed against a real live run — a genuine `/speckit-specify` invocation produced a correct, matching-correlation-ID started/completed pair in the DB. The `skill` key guess was right. |
| 7 | Two Claude Code sessions running Spec-kit skills in the same repo at the same time (e.g. two terminals, two different features) would both write to the same shared `.claude/.telemetry-state.json`, clobbering each other's in-flight state. | Open | Not solved. Single global state file per repo was a deliberate simplification for a single-developer POC; would need a per-session (or per-`session_id`) state file to handle concurrent sessions. |
| 8 | `speckit-implement` silently produced zero events on a real run (`specify`/`plan`/`tasks` all logged fine). Root cause: `repo_context()` derived `repo_root` from the hook payload's `cwd` via `git rev-parse --show-toplevel`. `implement` was actively editing files inside `src/tobi-faq-spike`, a **separate git repo** (submodule) nested in the project. If the session's tracked working directory drifted into that submodule at any point, `cwd`-based resolution would silently resolve to the submodule's root instead of the parent repo, `.specify/feature.json` wouldn't exist there, and the hook exits quietly with no event and no visible error. **Confirmed** — found `"cwd":".../src/tobi-faq-spike"` directly in the session's transcript JSONL, proving the working directory really did drift into the submodule (not just a plausible hypothesis). Also reproduced the exact failure via simulation and confirmed the fix resolves it. | Handled | `repo_context()` now prefers `$CLAUDE_PROJECT_DIR` (fixed at session launch, immune to in-session `cd` drift) over deriving `repo_root` from `cwd`, falling back to the old behavior only if that env var is unset. Reproduced the bug and verified the fix with `cwd` pointing at the submodule in both cases. The in-progress `implement` run that surfaced this was already missed for its `started` event — manually backfilled a state file with `started_at` set to discovery time (not the real start) so it at least gets a `completed` event; that one run's duration will be an undercount. |
| 9 | A real `plan → tasks → implement` chain, all invoked within a single conversational turn (no user interaction in between), silently lost the `completed` events for `plan` and `tasks` entirely — only `implement` (the last in the chain) got one. Root cause: the single-slot `.claude/.telemetry-state.json` assumes one skill runs to completion (via `Stop`) before the next one starts. `Stop` only fires once per turn, so when multiple skills are chained in one turn, each new `PostToolUse(Skill)` silently overwrote the previous skill's in-flight state before its `Stop` ever had a chance to fire. This is a distinct failure mode from #1 (`Stop` firing *too early*) — this is `Stop` firing *too late*, after several skills have already been clobbered. **Confirmed** via real DB data (`plan_started` → `tasks_started` → `implement_started` with zero completed events between them) and reproduced exactly via simulation. | Handled | `handle_post_tool_use` now checks for an existing in-flight state before overwriting it; if found, treats the new skill starting as an implicit completion signal for the previous one and synthesizes its `*_completed` event (using "now" as the completion time) before proceeding. Extracted the completion-posting logic into a shared `finalize_run()` used by both this path and `Stop`. The two real orphaned events this produced (`plan_completed`/`tasks_completed` for one spec) were manually backfilled with real durations and token counts computed from the session transcript, flagged `"backfilled": true` in their metadata for transparency. |
